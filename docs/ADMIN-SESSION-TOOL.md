# Отдельный инструмент администратора: новая сессия → очистка → выход

В Telegram-админке основного бота: **Товары и аккаунты → Новая сессия и очистка**. Прямая команда — `/session_tool`. Инструмент работает внутри существующего процесса, использует его Bot и переменные `TELEGRAM_API_ID`/`TELEGRAM_API_HASH`, не создаёт второго бота и не запускает новый polling.

## Источник: Session PR #1

По запросу в качестве источника обработки ввода зафиксирован [Afimin128899/Session PR #1](https://github.com/Afimin128899/Session/pull/1), commit `b51e3174268d41cf8641bb3ecd38a1468a79df76`. Из этого состояния взяты функции `normalize_phone` и `normalize_code`: ввод с/без `+`, международный префикс `00`, российский `8` → `+7`, пробелы/дефисы в коде, проверка пустого пароля 2FA.

В полном исходнике указанного PR нет очистки Telegram-данных или завершения старой авторизации. Поэтому запрошенный сценарий добавлен отдельным сервисом с подтверждениями и постоянным сохранением. Старая финализация PR #1, которая экспортировала API-ключи в JSON и удаляла файлы после отправки, не переносилась. Клиентам Telegram передаются только API-ключи текущего сервиса; ключи из загруженного JSON игнорируются.

## Использование

1. Администратор открывает инструмент **в личном чате основного бота**. Пользователи, помощники вне `ADMIN_IDS`, группы и партнёрские боты доступа не имеют. Тестовый магазин продолжает блокировать этот экран существующим DemoGuard.
2. Нажмите «Загрузить .session / ZIP». Отправьте собственную Telethon SQLite `.session` или ZIP с парами `.session + .json` в корне. Лимит — 20 МБ на загрузку и суммарную распаковку, до 100 элементов. Проверяются пути, ссылки, дубликаты, формат SQLite и ключ сессии; StringSession и tdata не принимаются.
3. Каждая задача сначала сохраняется как **черновик**, который не может забрать worker. Бот показывает полный список действий и кнопку **«Подтверждаю действия»**. «Продолжить очередь» не подтверждает черновики. Если сообщение потерялось или сервис перезапустился, откройте «Статус» → «Действия для ID».
4. После подтверждения бот проверяет исходную авторизацию, создаёт независимую новую авторизацию и проверяет соответствие аккаунта. Telegram определяет способ доставки кода. Автоматическое чтение разрешено только при доставке в приложение: `777000` и доступный `+42777`, отдельная граница ID для каждого чата, без зависимости от часов сервера. Недоступность чата и отсутствие нового сообщения различаются.
5. При необходимости бот запросит `/session_tool_input ID значение`. Для кода поддерживаются пробелы и дефисы из PR #1. Пароль 2FA из JSON используется, если указан; при необходимости доступен ручной ввод. Ввод относится только к конкретной задаче своего администратора, сообщение по возможности удаляется. Значения кода и пароля в ответ не повторяются и не логируются. Повтор кода словом `resend` возможен не более одного раза, только при разрешённых Telegram `next_type` и `timeout`, после ожидания timeout. Доставка не гарантируется.
6. До очистки новая авторизация сохраняется на постоянный диск: `.session`, `.json`, ZIP, fsync и ссылка в SQLite. Затем аккаунт очищается **через новую авторизацию**, результат повторно сохраняется. Только после этого отправляется один `LogOutRequest` **загруженной старой** авторизации. Сброс всех авторизаций не вызывается: другие новые авторизации сохраняются.
7. Новые файлы и ZIP остаются на диске, даже если отправка не удалась. Кнопка «Мои результаты» выдаёт только результаты текущего администратора. Если ссылка в SQLite не сохранилась, но ZIP записан, она восстанавливается без повторного выполнения операции.

## Что удаляется

Перед подтверждением перечисляются сброс профиля и username, удаление фотографий, контактов, папок, стикеров, черновиков, Избранного и истории диалогов; выход из групп и каналов, удаление каналов создателя и блокировка ботов; очистка платёжных данных, изменение приватности, завершение веб-авторизаций, установка срока автоудаления аккаунта в 30 дней. Действия необратимы. Выбор отдельных категорий внутри комплексной очистки не реализован.

При частичной очистке, неправильном аккаунте или ошибке сохранения исходная авторизация не отзывается. FloodWait сохраняется в постоянном ограничении аккаунта, автоматического повтора выхода нет. Отмена не откатывает уже выполненное удаление или принятый сервером выход. При таймауте выхода его фактический результат может быть неизвестен, но новая авторизация уже сохранена.

## Отдельно от продаж и каталога

Инструмент обрабатывает только явно загруженные администратором файлы. Он не перечисляет склад, не меняет аккаунты в MySQL, не создаёт товар, не назначает цену, не изменяет заказы, оплату, доступ покупателя или автоматическую переавторизацию склада. Если администратор загрузит копию авторизации, используемой товаром, отзыв исходной авторизации сделает эту копию в каталоге нерабочей. Используйте отдельные собственные сессии; перенос результата в магазин выполняется обычным существующим импортом по явному действию администратора.

Архивы, статусы, подтверждения и ручной ввод изолированы по Telegram ID администратора. Даже другой полный администратор не получает эти архивы через интерфейс. Доступ сервера к файлам и резервным копиям остаётся ответственностью владельца сервиса.

## Постоянный диск и настройки

- `ADMIN_SESSION_DATA_DIR`: отдельный приватный каталог. По умолчанию `<RAILWAY_VOLUME_MOUNT_PATH|DATA_DIR|runtime>/admin-sessions`.
- В Railway требуется подключённый Volume; каталог инструмента должен находиться внутри `RAILWAY_VOLUME_MOUNT_PATH`. Пример: Volume `/data`, `ADMIN_SESSION_DATA_DIR=/data/admin-sessions`. Если Volume не определён или каталог находится вне его, инструмент отключается, а магазин продолжает запускаться. Проверьте права записи для пользователя контейнера UID 10001.
- На VPS используйте постоянный приватный каталог с правами на запись для пользователя сервиса. `.env.admin-session.example` содержит только образец настроек.
- `ADMIN_SESSION_CONCURRENCY`: 1–8 задач, по умолчанию 1. SQLite-очередь сохраняет ожидание и паузу; одна активная операция на Telegram-аккаунт внутри инструмента. Отдельной общей блокировки с существующими операциями склада нет.
- `ADMIN_SESSION_RETENTION_DAYS`: 1–365 дней, по умолчанию 7, для исходных загрузок и загруженных секретов JSON. Новые сессии, резервные копии и их ZIP **не удаляются автоматически**.

Новые файлы хранятся в `new_sessions/<admin>/<task>/before_cleanup/` и `after_cleanup/`. Это копии одной новой авторизации. Если первоначальное сохранение не удалось, единственная рабочая копия остаётся в `recovery/<task>/` либо `work/<task>/`; стартовая очистка её сохраняет. Старт удаляет staging и обычные временные копии, а выполнявшиеся задачи помечаются «прервана» без автоматического повторения опасных запросов. Ожидающие подтверждённые задачи продолжаются; при отзыве администратора они отменяются до подключения клиента. Ручной ввод через память после рестарта нужно начинать заново новой задачей.

Сессии и пароли JSON на диске не шифруются приложением, доступ к каталогу и backups должен быть ограничен. Не добавляйте каталог, SQLite, `.session`, ZIP или `.env` в Git. Вторая копия магазина на другом сервере не защищается локальной SQLite-блокировкой; для одного токена нужен один polling-процесс. Архивы не удаляются сами — следите за свободным местом.

## Офлайн-проверки

```sh
pip install -r requirements.txt pytest==8.4.2 pytest-asyncio==1.2.0
python -m pytest -q tests/test_admin_session_tool.py tests/test_admin_session_workflow.py tests/test_admin_session_protocol.py tests/test_admin_categories.py tests/test_bot_ux.py tests/test_session_inventory_jobs.py::AuthorizationTests tests/test_session_inventory_jobs.py::ArchiveTests tests/test_session_inventory_jobs.py::LeaseTests
```

Тесты используют синтетические настройки, временный SQLite и поддельные клиенты. Настоящие `.env`, сессии и MySQL не подключаются. Проверяются права, основной/партнёрский бот, приватный чат, подтверждения, отдельный ручной ввод, порядок сохранения/очистки/выхода, отсутствие отзыва новых авторизаций, ошибки диска/отправки, отмена, FloodWait, восстановление и прежние кнопки админки. CI запускает этот набор.

Нужна отдельная проверка на собственном тестовом Telegram-аккаунте: реальная доставка кода и 2FA, доступность служебных чатов, результаты всех операций очистки и фактический выход из исходной авторизации. Также проверьте перезапуск с Volume и выдачу архива на рабочем сервере. Успех офлайн-тестов не означает полной проверки Telegram-интеграции.
