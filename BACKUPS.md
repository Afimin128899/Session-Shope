# Резервные копии базы

На Ubuntu 24 `sudo bash install.sh` устанавливает restic и клиент MariaDB,
создаёт зашифрованный репозиторий, systemd-сервисы и таймеры. Первая копия и проверка
выполняются сразу. Бот продолжает работать во время копирования.

- Ежедневная копия: около **04:00 МСК**, со случайной задержкой до 10 минут.
- Недельная проверка: **воскресенье около 05:00 МСК**, задержка до 10 минут.
- Хранятся 14 ежедневных, 8 недельных и 6 месячных точек, с дедупликацией.
- По умолчанию: `/var/backups/session-shope/restic`.
- Конфигурация: `/etc/session-shope/backup.env`, права `600`.
- Ключ: `/etc/session-shope/backup-password`, права `600`.

**Локальная копия не переживёт уничтожение диска или переустановку VPS.**
Скачайте ключ через защищённый SSH/SFTP и сохраните отдельно в надёжном месте,
затем подключите внешний репозиторий, когда выберете хранилище. Ключ не нужно
публиковать в GitHub, присылать в чат или размещать в самом backup-репозитории.
Без исходного ключа зашифрованные копии восстановить нельзя.

## Что копируется и проверяется

В репозиторий потоково отправляется SQL базы, а не файлы приложения. Полного
незашифрованного `.sql` на диске не создаётся. Пароль MariaDB передаётся через
временный клиентский конфигурационный файл с правами `600`, не через аргументы
процесса. Оригинальный `.env` с токеном бота не включается в копию.

Для локальной MariaDB используется Unix-сокет. Удалённые подключения используют
TLS с проверкой имени и сертификата; собственный CA задаётся через
`BACKUP_DB_SSL_CA` в `backup.env`, без отключения проверки TLS.

Каждая завершённая копия проверяется restic. Недельная проверка читает все
зашифрованные данные, восстанавливает SQL в **новую временную базу** с отдельным
пользователем, имеющим права только на эту базу, проверяет таблицы и удаляет только
созданные тестовые объекты. Рабочая база не перезаписывается. Для удалённой MySQL
таймер выполняет проверку целостности restic; полноценное SQL-восстановление нужно
проводить на отдельном тестовом сервере с соответствующими правами.

Два задания не могут одновременно менять репозиторий: операции сериализуются
локальной блокировкой. Неуспешный SQL-dump не считается успешной копией; частичный
снимок этой попытки удаляется. Старые корректные снимки не удаляются из-за ошибки
создания новой копии. Retention применяется после успешного сохранения.

## Проверка состояния и ручной запуск

```sh
systemctl list-timers 'session-shope-backup*' --no-pager
systemctl status session-shope-backup.service --no-pager -l
journalctl -u session-shope-backup -u session-shope-backup-check -n 40 --no-pager

# Создать копию сейчас:
sudo systemctl start session-shope-backup.service

# Проверить восстановление сейчас:
sudo systemctl start session-shope-backup-check.service
```

Для действующего проекта обновление без переустановки:

```sh
cd /opt/session-shope
git pull --ff-only origin main
sudo bash install.sh
```

Сервисы остаются `inactive (dead)` после успешного oneshot-задания — это нормально.
Результат должен быть `status=0/SUCCESS`, таймер — `active (waiting)`.

## Подключение внешнего хранилища

Для безопасного переключения после выбора хранилища запустите на VPS:

```sh
cd /opt/session-shope
sudo .venv-miniapp/bin/python -m deploy.connect_backup --project /opt/session-shope --type s3
# Для SFTP вместо s3 укажите sftp.
```

Адрес и ключи вводятся в терминале; секреты вводятся скрыто. S3 требует HTTPS,
SFTP — заранее проверенный SSH host key в known_hosts root и настроенный SSH-ключ.
Ключ шифрования сохраняется прежним. Конфигурация переключается только после
успешного создания и проверки первой внешней копии. При ошибке локальные задания
продолжат использовать прежний репозиторий. Для SFTP используется строгая проверка
host key и запрет интерактивного запроса пароля.

Для ручной настройки измените `/etc/session-shope/backup.env` на сервере, сохраняя права `600`.
Не меняйте ключ уже существующего репозитория.

Для S3-совместимого сервиса задаются `RESTIC_REPOSITORY` вида
`s3:https://storage.example.com/bucket/session-shope`, `AWS_ACCESS_KEY_ID` и
`AWS_SECRET_ACCESS_KEY`. Значения вводятся только на сервере. Для SFTP используется
`RESTIC_REPOSITORY=sftp:backup-user@backup-host:/path/session-shope` и SSH-ключ,
проверенный known_hosts и доступный root-сервису. Не отключайте проверку ключа
сервера. Также restic поддерживает транспорт `rclone:remote:path` после отдельной
установки и безопасной настройки rclone.

После настройки выполните из каталога проекта:

```sh
sudo .venv-miniapp/bin/python -m deploy.setup_backups --project /opt/session-shope
```

Будут проверены или инициализированы настроенный репозиторий, выполнены новая
копия и проверка восстановления. Переключение репозитория не переносит старые
снимки автоматически. Локальные копии остаются на месте; не удаляйте их, пока
внешняя копия и ключ не проверены.

## Восстановление после потери VPS

Сначала разверните приложение и MySQL на новом сервере. Верните отдельно
сохранённый ключ, настройте доступ к внешнему репозиторию и выполните проверку
восстановления. Перед заменой рабочей базы остановите бот и сделайте копию текущих
данных. Затем импортируйте SQL выбранного снимка в целевую базу через локальный
клиент MariaDB с закрытым конфигурационным файлом, после чего запустите бот.
В этом обновлении намеренно нет кнопки перезаписи рабочей базы из Telegram.

Данные приложения не заменяют настройки сервера: BOT_TOKEN, Telegram API ID/Hash
и доступ к внешнему хранилищу нужно восстановить отдельно. Код и зависимости можно
снова получить из репозитория.
